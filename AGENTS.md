# AGENTS.md — Besslov

Инструкции для AI-агентов и разработчиков, работающих с сайтом «бесслов».

## Цель проекта

Это публичный русскоязычный сайт преподавателя русского языка и литературы для 8–11 классов. Важны спокойный, поддерживающий тон, доступность и аккуратная адаптивная вёрстка. Production-сайт: https://besslov.vercel.app

Основные пользовательские сценарии:

1. Просмотреть информацию о занятиях на главной странице.
2. Перейти на страницу отзывов.
3. Открыть форму и отправить заявку.
4. Читать сайт на мобильном устройстве и с клавиатуры.

Не добавляйте вымышленные отзывы, результаты учеников, цены, контакты или изображения людей. Публикуйте только контент, явно предоставленный владельцем сайта.

## Быстрый старт и команды

Проект использует Node.js >= 22.13.0 и pnpm 11.

```sh
pnpm install
pnpm exec next dev
pnpm build
pnpm lint
pnpm db:generate
```

- Для локальной разработки используйте `pnpm exec next dev`. Скрипт `pnpm dev` унаследован от Sites/Cloudflare-версии и с публичным GitHub-репозиторием может не работать, потому что его служебные скрипты намеренно не публикуются.
- Перед передачей изменений запускайте как минимум `pnpm build`; после изменения TS/TSX также запускайте `pnpm lint`.
- Автоматических unit/E2E-тестов пока нет. Для UI-изменений выполните ручную проверку главной страницы, `/reviews`, мобильной ширины и формы.
- Не редактируйте `pnpm-lock.yaml` вручную. Меняйте его только командой `pnpm install` после изменения зависимостей.
- Не меняйте версию Node или фреймворк без явной необходимости и согласования.

### Маршруты

- `/` — основная страница.
- `/reviews` — отзывы и истории учеников.
- `/api/enquiries` — принимает только `POST` с JSON-заявкой.

Добавляя маршрут, используйте App Router: `app/<segment>/page.tsx`. Если маршрут зависит от данных запроса или приватного состояния, явно определите его стратегию рендеринга и не допускайте утечки персональных данных в HTML или логи.

## Контент и отзывы

`app/reviews/stories.ts` — единственное место для публикации историй учеников. Каждый объект `studentStories` должен содержать:

- понятный заголовок и нейтральное обозначение ученика;
- контекст;
- четыре этапа: старт, разбор ситуации, подготовка, результат;
- текстовый отзыв и, только при явном согласии, изображение с корректным `alt`.

Не публикуйте имя, контакты, скриншоты переписок или фото несовершеннолетних без явно подтверждённого разрешения владельца и человека на фото. Не храните такие материалы в issue, комментариях коммитов или примерах кода.

## Дизайн и UI

Стили намеренно собраны в `app/globals.css`; не переносите их в случайные inline-style без причины.

- Основной шрифт и шрифт заголовков: **Golos Text**.
- Декоративный рукописный шрифт: **Caveat**, только для акцентных подписей и логотипа.
- **Balsamiq Sans запрещён**: не добавляйте его обратно в CSS, assets или зависимости.
- Локальные шрифты подключены из `public/assets/fonts.css`; для файлов `.woff2` всегда указывайте `format('woff2')`.
- Базовые цветовые токены находятся в `:root` в `app/globals.css` (`--pink`, `--lime`, `--blue`, `--ink`, `--paper`). Используйте их вместо близких произвольных hex-значений.
- Сохраняйте существующую визуальную систему: бумажный фон, подчёркивания, заметки, мягкие скругления, но без перегрузки эффектами.
- Все новые изображения кладите в `public/assets/`, оптимизируйте их и добавляйте содержательный `alt`. Не заменяйте портрет преподавателя без явного запроса.
- Любое интерактивное действие должно быть доступно с клавиатуры, иметь видимый `:focus-visible` и понятную aria-метку, когда текстовой метки недостаточно.
- После изменения CSS проверьте ширины около 1440 px, 900 px, 600 px и 360 px. Не ломайте существующие media queries.

## Компоненты и код

- Пишите TypeScript в строгом режиме. Не используйте `any`, если можно описать тип.
- Используйте alias `@/` для импортов из корня проекта.
- По умолчанию создавайте Server Components. Добавляйте `"use client"` только при необходимости состояния, событий, эффектов или browser API.
- Не смешивайте сетевой доступ, валидацию и сложную разметку в одном компоненте: выносите типы и валидацию в `lib/`, переиспользуемую разметку — в `components/`.
- Для UI-примитивов предпочтительны существующие компоненты из `components/ui/`; сохраняйте их API и доступность.
- Не выполняйте опасные миграции, удаление данных или массовое преобразование контента без явного запроса владельца.
- Тексты интерфейса — на русском, дружелюбные и короткие. Ошибки формы не должны раскрывать внутренние детали платформы.

## Форма и API заявок

Клиентская форма в `app/page.tsx` отправляет JSON на `POST /api/enquiries`.

`app/api/enquiries/route.ts` уже делает важные проверки: same-origin, тип контента, ограничение размера, JSON parsing и Zod-валидацию. При изменении API сохраняйте эти защиты или усиливайте их.

Правила:

- Поле `website` — honeypot; не удаляйте его без замены антиспам-механизма.
- `id` — UUID для идемпотентности. Сохраняйте защиту от повторной записи через `ON CONFLICT(id) DO NOTHING`.
- Не логируйте имя, контакт или полное тело заявки.
- Любое новое поле формы сначала добавляйте в Zod-схему, затем в API, БД и миграцию. Не полагайтесь только на клиентскую проверку.

## SQLite, Drizzle и Cloudflare D1

`db/schema.ts` использует SQLite-диалект Drizzle. В исходной платформе данные должны храниться в Cloudflare D1 — управляемой SQLite-совместимой базе — через binding `DB`.

Таблица `enquiries` содержит `id`, `name`, `contact`, `chaos`, `format`, `consent`, `created_at`. Структура таблицы и SQL-миграция должны оставаться синхронизированными.

Критичное ограничение: production сейчас развернут на **Vercel**, а реализация `db/enquiries.ts` обращается к модулю `cloudflare:workers`. Поэтому без Cloudflare D1 binding форма на Vercel корректно покажет ошибку недоступности хранилища, но не сохранит заявку.

Перед изменением хранилища:

1. Согласуйте целевую платформу (Cloudflare D1, Vercel Postgres/Neon, другой backend).
2. Не храните ключи в исходниках, `.env.example` или README.
3. Добавляйте переменные только через настройки платформы; в репозиторий коммитится лишь безопасное имя переменной в документации.
4. Создавайте миграцию через `pnpm db:generate`, проверяйте SQL и применяйте её отдельно к production-базе.
5. Не меняйте существующие типы/колонки разрушительно без плана миграции и резервной копии.

## Конфигурация

- `package.json` — зависимости и команды. Production build: `next build`.
- `next.config.ts` — место для Next.js redirects, headers и image-настроек. Сейчас используются настройки по умолчанию.
- `tsconfig.json` — strict TypeScript и alias `@/*`.
- `postcss.config.mjs` — Tailwind CSS через PostCSS.
- `components.json` — настройки и aliases shadcn/ui.
- `drizzle.config.ts` — генерация SQLite-миграций в `drizzle/`.
- `.npmrc` — отключает audit/funding/update notifications; не содержит секретов.
- `.gitignore` — исключает зависимости, build output, `.env*`, `.vercel/` и локальное состояние.

Не добавляйте обратно Cloudflare-only `vite.config.ts` или внутренние Sites-конфиги: Vercel собирает проект как Next.js.

## Git и Vercel

Репозиторий: https://github.com/DaemonSharps/Besslov-site  
Production branch: `main`  
Vercel project: `besslov`

Каждый push в `main` запускает production-деплой. Перед изменением:

1. Просмотрите существующий код и не перезаписывайте несвязанные изменения.
2. Делайте небольшие тематические коммиты в повелительном наклонении, например: `Add student story card`.
3. Перед коммитом выполните релевантные проверки.
4. После push проверьте Vercel build status и production URL.
5. При ошибке сначала получите build logs, исправьте первопричину и только затем делайте новый commit. Не меняйте настройки Vercel наугад.

## Definition of done

Задача считается завершённой, когда:

- изменён только необходимый код и документация;
- `pnpm build` проходит или причина внешней блокировки явно зафиксирована;
- `pnpm lint` запущен для TS/TSX-изменений;
- мобильная и desktop-вёрстка не регрессировали;
- ссылки, форма и `/reviews` проверены, если они затронуты;
- нет новых секретов, персональных данных, ложных отзывов или тяжёлых неоптимизированных assets;
- Vercel production-деплой имеет статус READY, если изменения были отправлены в `main`.
